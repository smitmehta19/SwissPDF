# SwissPDF parity plan: iLovePDF + Stirling PDF, proven on real files

Date: 2026-10-17. Status: DRAFT, waiting for approval.
Inputs: `docs/research/ilovepdf-rea.md`, `docs/research/stirling-pdf.md`, `docs/research/swisspdf-audit.md`, `docs/research/test-corpus.md` (131 real files, 352 MB, in `test-corpus/`, gitignored).

## Goal and definition of done
- Every tool that iLovePDF and Stirling PDF offer (minus the out-of-scope list) exists in SwissPDF, runs fully in the browser, and passes on real corpus files.
- Done = every row in the parity checklist (built in U0, `docs/plans/parity-checklist.md`) is green: tool works on at least its listed real files, output re-opens in pdf.js and MuPDF, content checked (text, page count, geometry), no crash on the large files.
- Look and feel: Stirling-style workbench (left tool panel with search, centre workbench with viewer / page editor / file grid, right options panel), iLovePDF option patterns (captioned option cards, 3x3 position grid, live "N PDFs will be created" line, result screen with "continue with another tool"). Own name, palette and icons: no copied branding or proprietary code.

## Out of scope (with reason)
| Item | Reason |
|---|---|
| AI Summarizer, Translate, Smart split/redact, AI form detect | Needs an LLM server: breaks the "files never leave your device" promise |
| Multi-signer email requests, eIDAS certified signing service | Needs accounts + server + paid CA |
| Google Drive / Dropbox pickers | Parked: possible later (pickers are client-side), not core |
| URL to PDF (fetch a live site) | Browser CORS blocks it; paste HTML stays |
| Mobile app QR pairing (Scan to PDF) | Replaced by camera capture in the browser (U5) |
| PDF/A validation (veraPDF), Calibre ebook formats | No WASM exists; EPUB export done in plain JS instead |
| Timestamp authority (TSA) signing | Most TSAs block browser CORS; try in U5, drop if blocked |

Each unit: scope file written and approved before its build; built by parallel developer agents on non-overlapping folders; reviewed by a separate reviewer agent + the corpus runner; nothing ships without its corpus rows green.

## Testing method (all units)
- Runner: `scripts/corpus-test/` (Playwright, Chromium, real UI, real file inputs from `test-corpus/`). Output: `docs/test-results/<date>-<unit>.md` scorecard + JSON.
- Checks per output: opens in pdf.js and MuPDF; page count; text present/absent where expected; page boxes and rotation; size limits (compress never larger); time and memory on `large/`.
- Health self-test stays as a quick smoke test; corpus runner is the real gate.

## Cost
- Money: 0. All libraries free/open source (qpdf-wasm Apache-2, fontkit MIT, Noto OFL, pkijs BSD, Ghostscript WASM AGPL). Hosting stays GitHub Pages free.
- Effort: roughly U0 small, U1 large, U2 large, U3 large, U4 medium, U5 very large (split into U5a/U5b if needed), U6 small. Per sprint max 3-4 developer agents + 1 reviewer.

## Sprint 1 proposal: U0 only
- In: corpus runner, parity checklist, baseline scorecard of all 30 tools, project `CLAUDE.md`, comma-password hotfix.
- Out: any other tool fix (findings go into the scorecard, fixed in U1+).
- Done: runner runs end to end on the corpus; scorecard lists pass/fail per tool per file with evidence; checklist covers every in-scope iLovePDF + Stirling tool.
